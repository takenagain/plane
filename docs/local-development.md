# Local development with Podman

The development stack supports rootless Podman through `podman-compose`.
Use the Node/pnpm versions in `package.json`, the Python version in
`apps/api/.python-version`, and the uv version required by
`apps/api/pyproject.toml`.

## Start a fresh checkout

On a fresh checkout, run `./setup.sh` to create environment files and install
JavaScript dependencies. The setup script copies example files over existing
`.env` files, so preserve an existing configuration before using it.

Start the infrastructure, API, workers, and database migrations:

```bash
podman-compose -f docker-compose-local.yml up -d --build
```

The local Compose file publishes its services on loopback:

| Service         | Address               |
| --------------- | --------------------- |
| API             | http://localhost:8010 |
| Valkey          | localhost:6379        |
| S3 storage      | http://localhost:9000 |
| Storage console | http://localhost:9090 |

For this Compose configuration, set `VITE_API_BASE_URL=http://localhost:8010`
in the web, admin, and space `.env` files, and set
`API_BASE_URL=http://localhost:8010` in `apps/live/.env`.
Set `WEB_URL=http://localhost:3000` in `apps/api/.env` and ensure the browser app
origins are included in `CORS_ALLOWED_ORIGINS`.
The example API URL uses port8000; Compose publishes the API on8010 instead.

For web requests to `/api` and `/auth` to reach the same backend, also set
`VITE_DEV_API_PROXY=http://127.0.0.1:8010` in `apps/web/.env`.

Start the host development servers:

```bash
pnpm dev
```

Web runs on3000, administration on3001, spaces on3002, and live collaboration
on3100. The live service runs the built `dist/start.mjs` entrypoint explicitly;
its package metadata is regenerated by tsdown during builds.

## Stop and inspect

```bash
podman-compose -f docker-compose-local.yml ps
podman-compose -f docker-compose-local.yml logs api
podman-compose -f docker-compose-local.yml stop
```

Named volumes retain database and object-storage data. Keep `.env` files,
generated credentials, database backups, browser profiles, screenshots, and
machine-specific launchers out of version control.

## Kubernetes

The community Kubernetes deployment documentation is in
[deployments/kubernetes/community](../deployments/kubernetes/community/README.md).
A local source-mounted Kind deployment can use rootless Podman for its node.
Local cluster mounts, image archives, secrets, and user-systemd port forwards
belong to the machine configuration rather than the application source.

## Verification before committing

For frontend changes, run the web unit suite, the live suite when applicable,
and the full browser suite:

```bash
pnpm --filter=web test:unit
pnpm --filter=live test
pnpm test:e2e
```

The existing E2E fixtures need API-container access to seed their test account.
For Compose, use the API container/project name from `podman-compose ps` and
set `E2E_API_URL=http://localhost:8010`. Keep `BASE_URL=http://localhost:3000`.
The global setup currently invokes the Docker CLI. A local adapter lets those
commands use Podman without installing a Docker daemon:

```bash
mkdir -p tmp/podman-bin
cat > tmp/podman-bin/docker <<'SH'
#!/bin/sh
if [ "${1:-}" = compose ]; then
  shift
  exec podman-compose "$@"
fi
exec podman "$@"
SH
chmod +x tmp/podman-bin/docker

PATH="$PWD/tmp/podman-bin:$PATH" \
  BASE_URL=http://localhost:3000 \
  E2E_API_URL=http://localhost:8010 \
  E2E_COMPOSE_PROJECT=plane \
  CONTAINER_RUNTIME=podman \
  pnpm test:e2e
```

Replace `plane` with the Compose project name when it differs.
See [the development environment notes](test-dev-environment-setup.md) and
[e2e/playwright.config.ts](../e2e/playwright.config.ts) for configuration details.
